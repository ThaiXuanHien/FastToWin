# Reward events — approved Issue #18 implementation design

Authority: https://github.com/ThaiXuanHien/FastToWin/issues/18, approved 01/10/2026; user explicitly requested continued implementation on 06/10/2026. This document records implementation choices within that approved scope. Admin foundation, gifts, maintenance and analytics are accepted dependencies at local commit `c875d65cedba800fc3b73903608425ceb9f719b9`.

## Behavior

- Admin creates bilingual event drafts with an IANA display timezone, UTC start/end, independent GOLD/XP factors of 1 or 2, and a nonempty CASUAL/RANKED set. Draft editing requires Owner/Operator; scheduling/cancellation requires Owner. Current server roles, Origin/CSRF, version, request identity and transactional audit precede disclosure/replay. Support cannot operate draft campaigns; published player information contains no administrative identities or internal reasons.
- DRAFT → SCHEDULED → ACTIVE → ENDED; CANCELLED is terminal. Effective scheduled/active/ended state is derived from server time and `[startsAt, endsAt)`, without requiring a cron to update rows. Publishing freezes definitions; editing a published definition is rejected. Cancellation prevents later starts but never changes an existing match snapshot. Ended history is read-only. A live-period draft may be published if its end is still future; earlier matches are never recalculated.
- Match rewards apply only to existing eligible online CASUAL/RANKED matches. Intentional departure still yields zero. Tournament, offline, Gem, Elo, missions, attendance, achievements and administrative gifts are excluded. The largest GOLD factor and largest XP factor win independently; no multiplication between events. Reward sources identify all definitions contributing a factor above 1, in deterministic order.
- The ranked win example remains 100 GOLD +30 XP base, 100 GOLD +30 XP bonus, 200 GOLD +60 XP total with both x2. CASUAL uses its existing base reward. A no-bonus snapshot has factors 1/1 and no contributing event sources.

## Authoritative start and durable result

Use a focused `events` module and an `EventRewardSource.withStartCatalog` seam. PostgreSQL acquires a shared transaction advisory lock `7421092187350` for the published event catalog; scheduling/cancellation takes its exclusive form after the existing admin authorization lock `7421092187349`. The catalog is read before the engine transition callback. At the actual `Room.startMatch` boundary, take the current server time and synchronously resolve the immutable catalog to a per-match snapshot. The short callback runs the existing transition under the engine mutex; it must not perform new event JDBC I/O there. This ordering makes concurrent cancellation/publishing and match start serializable without a stale periodically refreshed event cache. Never acquire the event gate while already holding the engine mutex. Existing tournament starts use a neutral snapshot and do not need this gate.

The callback must also not borrow another database connection while its event transaction is held. Existing quota consumption currently happens inside the engine start routines and must be prepared before entering the event gate, with a per-match admission identity and final recheck of participants/room/maintenance. A changed or failed attempt must remain safely retryable against the same quota receipt, not silently charge a different match; abandoned reservations need explicit rollback/recovery. Keep storage outside the short gate/engine transition and test pool-size2 plus a queued scheduling writer. This is an integration requirement, not permission to assume an unlimited pool or add an extra infrastructure pool without justification.

Each new/rematch uses a new snapshot. Store it in `StoredActiveRoom`, `CompletedMatch`, and completed-match database data. Legacy snapshots default to neutral and must not be retrospectively resolved against current campaigns. Restore, delayed completion, retry, pending settlement and cancellation preserve original sources and factors. Persist the start snapshot with the active room before exposing gameplay; failed durable persistence must not advertise a playable event match with an unrecorded configuration. Preserve the existing accepted maintenance admission, activation, recovery and quota behavior rather than bypassing it.

`PostgresMatchResultRepository` derives base/bonus/total from the frozen context and intentional-leave flag. The match/player reward breakdown, stats, total MATCH wallet transaction, and earned-asset leaderboard accounting use the existing successful result transaction. Unique match/result and `(user, MATCH, matchId)` behavior prevents retry double awards. Never add a separate EVENT_BONUS wallet source that counts the same reward twice. Reward configuration and result breakdown are trusted internal data, never accepted from player commands.

The default no-event source preserves existing base-game behavior in legacy/test/no-DB environments. When a configured durable event source fails, a new eligible match cannot silently pretend no event exists; reject that start safely without corrupting room/quota state. Existing frozen matches can finish without querying the event catalog. No-DB admin/public event storage explicitly reports unavailable. In-memory event/admin repositories support equivalent transactional tests.

## HTTP and compatible protocol

Admin API uses `/admin/api/events` and per-ID draft/preview/schedule/cancel/detail endpoints, existing pagination default25/max100, bounded search/status inputs, and safe errors. Public player API uses network-only `/api/events` and `/api/events/{id}`. List exposes published active/upcoming events, server time and pagination; details can retain ended/cancelled published history. Draft IDs return404 publicly. All paths use no-store and existing same-origin routing/Caddy policies. Publication/cancellation requests carry expectedVersion, reason, requestId; previews bind the exact definition/version with a server-calculated preview token. Current authorization is checked before replay.

Add serializable source/frozen-reward/breakdown DTOs in a separate protocol file. Extend existing game/history/detail snapshots only with optional/defaulted properties. Do not add a new unsolicited WebSocket message or NotificationKind enum for this feature. Verify the old JSON shape with a serializer ignoring unknown fields, and legacy stored JSON with missing fields. Player HTTP event loading uses a controller with account/view/language/request fences and explicit unavailable/loading/empty states. The client never multiplies a guessed reward to claim an award; online result values come from the server breakdown. Offline remains neutral.

## UI

Apply `.agents/skills/ui-ux-pro-max/SKILL.md`, existing `design-system/fast-to-win/MASTER.md` and white Material admin override. The new admin section is a paginated list/history with one create action and native modal draft/preview/confirmation/detail flows. Familiar edit/view/refresh/next/back utilities are labelled48px icons; form labels and Save/Cancel/Schedule remain readable. Preview displays both languages, exact timezone/time interval, match modes and GOLD/XP factors, overlap max-not-stack policy, and conflicts. Holiday presets create editable drafts only: lunar New Year dates are supplied by admin, annual repetitions/publication are never automatic, no gender/job targeting. Include the approved eight holiday suggestions.

The existing arcade home gains a compact active-event banner and a details sheet/screen. Event data uses Vietnamese/English and the selected language fallback; times explicitly identify display timezone. The result shows base, bonus, total and frozen event sources; expiry/cancellation of the live event does not erase the result explanation. Do not restyle the whole player application or cover an active match with an event popup.
