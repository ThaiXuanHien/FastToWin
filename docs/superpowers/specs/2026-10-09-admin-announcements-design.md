## Content, identity and publication

An announcement has a UUID, version Int1..2147483647 with checked increment, immutable first publication, creator/publisher/change/cancellation facts, bilingual title1..160 and body1..4000 UTF-16 units, category GENERAL/EVENT/MAINTENANCE/COMPENSATION, priority Int0..100 default0, required UTC `[startsAt,endsAt)` bounded0..253402300799999, always an in-app channel, optional Home banner and explicit pushEnabled defaultfalse. Draft reasons and cancellation/audit notes are internal. Published copy cannot be edited; an optional supersedesAnnouncementId points to a previously published announcement for a correction. Ended/cancelled items are labelled historical rather than erased by the schedule.

Owner/Operator create/edit/preview drafts; only Owner publishes/cancels; Support reads history/reports. Current role/session, exact Origin/CSRF, bounded strict JSON, positive expectedVersion, requestId `[A-Za-z0-9_-]{1,128}` and reason1..500 without control characters precede replay. Actor/request replay is fingerprinted across announcement operations and retains the immutable committed typed result. Changed payload409 and revoked roles cannot replay. Publication rejects an already ended interval, binds the full normalized definition and sorted recipient set in its preview token, freezes recipients/content and writes audit/replay atomically. All new counts, report totals and pagination totals are decimal strings.

ALL_REGISTERED snapshots registered/nondeleted accounts at publication, including banned-but-not-deleted accounts as in gifts; USER_IDS accepts1..10000 canonical UUIDs, reports duplicates and blocks missing/guest/deleted IDs. No activity, app-version, platform or guest targeting is inferred. An announcement is not a gift campaign, cannot choose wallet source and never awards/reclaims assets or changes event/maintenance settings.

## Internal actions and compatibility

Action is a typed NONE/REWARD_EVENT/GIFT_MAILBOX/APP_UPDATE destination. NONE and APP_UPDATE have no target ID; REWARD_EVENT requires an existing published event UUID; GIFT_MAILBOX requires an existing published ordinary/compensation gift campaign UUID. References are checked before publication. Cancellation/expiry of a linked entity does not grant access or remove a player's entitlement; existing event/mailbox readers enforce their own authority. APP_UPDATE opens an internal update information screen using the existing AppUpdateBridge capability; it does not accept a URL, configure a store updater or apply an update automatically. Native no-op hosts explicitly show their unsupported capability. Corrections link only by validated internal announcement ID. All copy is plain text; HTML/scripts/URLs are never executed or treated as action URLs.

The existing NotificationKind/NotificationDestination enum values and NotificationsData discriminator remain unchanged on the wire. NotificationSnapshot receives one default-null `announcement` context with public UUID, bilingual copy, category, schedule, priority, derived state, typed action/reference and correction reference. Announcement snapshots use legacy COSMETIC/PROFILE values with null actionData and plain admin-authored fallback text selected using the user's stored notification language, without adding a prefix beyond the validated copy bounds. Updated clients recognize the optional context and render an admin category/action; old readers ignore it and retain a safe existing icon/profile action instead of receiving an unknown enum. Old-shaped protocol readers must decode the actual new NotificationsData payload before acceptance; missing metadata must decode null. No new WebSocket discriminator is introduced.

IDs use reserved `admin-announcement:<UUID>`. Client SyncNotifications rejects any announcement context or this prefix, even if legacy fields/template otherwise look valid; clients never author or echo server announcements through that sync path. No client-supplied context can become authoritative.

## Persistence and shared notification authority

AnnouncementRepository owns synchronous AnnouncementTransaction operations on one JDBC Connection/copied memory state, including `admin: AdminTransaction`, the existing notification persistence writer and announcement definitions/recipients/replays/preferences/push attempts. NotificationRepository exposes the announcement authority, default unavailable for no-op/disconnected storage. Its existing social notification APIs reuse a connection-bound notification helper; an announcement transaction never calls their suspending public methods or opens a second connection. The memory implementation shares the same notification state and commits it only with successful admin/announcement state. Existing room invitations and social notifications retain their behavior.

Use the next additive migration V58. Preserve all applied migrations. Widen notification title/message only to accommodate validated server copy; legacy client sync retains its120/300 limits. Add nullable metadata/source mapping and announcement/recipient/request/preference/push-attempt storage. Unique `(announcement_id,user_id)` and existing `(user_id,notification_id)` prevent duplicate materialization. Frozen recipient IDs and durable stored/read/hide/push facts survive recipient deletion for reports; deleted users are skipped rather than inferred into a new audience. No token/password/provider diagnostic enters public DTOs or stored audit summaries.

Admin mutation locks global advisory7421092187349 before announcement rows and recipients. Delivery/push claims take announcement then recipient/user/notification locks consistently. Legacy read/dismiss mutations touching announcement receipts take recipient rows in stable order before notification rows, avoiding the inverse order of delivery; they never acquire the announcement/admin lock. Actual PostgreSQL tests must cover this seam and hard deletion. Atomic materialization inserts the existing notification and its checkpoint together; audit failure, statement failure or coroutine cancellation rolls back both. There is no wallet or second reward engine in this repository.

## Delivery, history and device state

Published due announcements materialize in bounded batches with durable per-recipient checkpoints and stable UUID ordering. Nothing is created before startsAt. Restart/catch-up after endsAt still materializes frozen recipients' history as expired, but never creates an active banner or sends late push. Cancellation stops unmaterialized work and keeps existing notifications as cancelled history. A canceled scheduled announcement does not create new notifications. Recipient deletion records a skip. Delivery and cancellation serialize on the announcement row; no batch continues after cancellation commits.

Existing read/dismiss operations persist announcement receipt read/dismiss facts too. Reading does not hide the banner. A separate hide-banner mutation affects only that user's banner, not the in-app history or a gift. Dismissing an inbox item may hide its banner; schedule/cancellation alone preserves readable history. Mutation retries are idempotent and authenticated. Device reloads fetch server state, not a local-only dismissal flag.

Registered-player HTTP routes under `/api/announcements` provide paginated inbox, detail, active banners, read/read-all, dismiss/dismiss-all, hide-banner and separate admin/event push preferences. Counts are exact strings, replies include serverNowEpochMillis, page default25/max100, no-store/nosniff and safe400/401/403/404/409/503. Bearer authentication checks current account; guest access is rejected. Full history is paginated rather than limited to the older WebSocket inbox's100 snapshots. The existing NotificationsData projection remains compatible for old clients. Every concrete DTO and method name is documented by its owning backend task before UI work.

## Optional push with conservative outcomes

Admin/event consent is a separate per-user HTTP preference record with defaultfalse, optimistic version and idempotent same-value retry. Existing UpdatePushPreferences messages continue to update only their four legacy categories; an old device cannot erase the new consent. GENERAL/MAINTENANCE/COMPENSATION require admin consent, EVENT requires event consent. Use the current existing token and notification language at the push claim; no new multi-device token registry is implied.

Push always follows durable in-app materialization. It is explicitly opted into per announcement, and publication still succeeds if the existing configured provider is unavailable; preview/confirmation/report explain that push may not send while in-app delivery remains. No UI action configures or enables production Firebase. Push copy uses the full title and a code-point-safe first240 UTF-16 units of the selected-language body, with the full body in-app; preview labels this shortened reminder. The existing push service gains a narrowly scoped raw bilingual announcement method/configured capability without changing social/reminder behavior.

Each announcement/user has at most one committed push attempt. Claim stores ATTEMPTING/attempt UUID before external I/O and checks current consent/account/token, active interval and cancellation; disabled/opted-out/no-token/unavailable/expired cases are explicit skipped/failed facts. External calls happen outside all database transactions with a20-second deadline. Once cancellation commits, no new attempt is claimed; an already claimed external attempt may complete and is reported honestly because it cannot be recalled.

Provider accepted maps to ACCEPTED, a definitive failure to FAILED, and timeout/interruption/ambiguous exception to UNKNOWN. ACCEPTED is provider acceptance, never proof of display/delivery/read. Ambiguous sends are never automatically retried. An unfinished ATTEMPTING older than120seconds becomes UNKNOWN on recovery rather than eligible for a resend. Completion conditionally settles only the matching attempt. UNKNOWN is recorded in durable attempt facts and an atomic system audit entry (`actorId=null`, internal reason/code and attempt/announcement IDs, no tokens/diagnostics). A new notification is the explicit way to issue a correction/reminder; there is no bulk retry button or auto-retry of UNKNOWN. Separate counters distinguish eligible, pending, stored, read, hidden/dismissed, skipped and push accepted/failed/unknown/in-flight/disabled/opted-out/no-token; they are not interchangeable or necessarily additive.
