## Incident and round behavior

An incident has an internal UUID and an immutable unique human incident key, canonical uppercase ASCII `[A-Z0-9][A-Z0-9_-]{0,127}`. It stores bilingual title1..160 and description1..4000 UTF-16 code units, matching existing gift field limits, affected UTC `[from,until)` within0..253402300799999, a nonblank internal cause/error code1..128, internal evidence1..10000, and an active responsible admin UUID. Title/description are player-safe; evidence/error code/admin identity are never player fields. Persist creator/latest editor and timestamps/version separately. Owner/Operator creates/edits/previews; Owner publishes/cancels; Support reads incident/round history only. Current role/session/Origin/CSRF must precede disclosure/replay and audit commits with mutations. Responsible admin must exist and be active when assigned; later deactivation does not rewrite historical ownership.

Incident edits are permitted only before any round has been published. First publication freezes its player-safe explanation and affected interval; later diagnostic corrections require a separate incident rather than rewriting delivered history. Do not derive status from logs or auto-publish compensation.

Round1 is the default. Creating it again is conflict, including with a new requestId. Supplemental rounds are explicit requests containing `expectedNextRoundNumber` exactly the current maximum+1, a separate nonblank supplemental reason1..500, and a preview showing previous claims. At most one draft round per incident may exist; a previous draft must be published or cancelled before another number is allocated. Never auto-increment on retry. Cancelled unpublished numbers remain used; the next explicit number can follow with supplemental reason and zero previous claims. Each round UUID is its existing gift campaign UUID and the COMPENSATION wallet source ID. Unique `(incident_id,round_number)`, `(campaign_id,user_id)` and wallet `(user,source_type,source_id)` protect identity. Supplemental round2 may intentionally pay a user who received round1; that is a new approved round, not a retry.

Round drafts choose ALL_REGISTERED or USER_IDS, canonical UUIDs1..10000 with duplicates reported and missing/guest/deleted IDs blocking publication. ALL_REGISTERED snapshots current registered/nondeleted accounts at publication, including accounts banned but not deleted as in accepted gifts. A generic registration-date audience is not an activity selector and is not offered here. Round fields are per-recipient GOLD/XP Int0..2147483647, at least one positive; receiving reasons VI/EN1..1000; availability UTC and expiry default exactly30days later, bounded and strictly increasing. No Gem/Elo/quota/fees/refund/cash operation is implied.

## Recipient source honesty

Existing sessions.last_seen_at is mutable and session replacement/deletion loses activity history. Completed matches have actual started_at/ended_at but do not establish complete activity coverage (active/failed/aborted/pending results and deleted participant identities are different sources). Existing analytics coverage concerns registration/item/payment facts, not incident activity. No trustworthy incident activity start/retention/completeness contract has been established. MVP exposes an authenticated capability response: ALL_REGISTERED and USER_IDS supported, ACTIVITY unavailable with a plain explanation. Reject an ACTIVITY request with400 `ACTIVITY_SOURCE_UNAVAILABLE`, including forged requests; do not turn unknown into zero or guess users from registration dates. Activity filters/app-version/platform/automatic crash targeting require their own verified source contract before exposure. The issue's insufficient-data acceptance path is exercised explicitly.

## Shared transaction and immutable publication

Extend the existing gift repository transaction with a `CompensationStore` bound to its exact JDBC Connection or copied memory state. The store owns incidents, round mapping and compensation replay receipts; it cannot open connections or commit. Admin operations retain advisory authorization lock7421092187349 and current authorization after waiting. No gift-service suspend call or nested repository transaction from inside a compensation transaction.

A focused shared internal gift-campaign helper centralizes existing normalization, audience selection/preview token and detail counters where needed. Public GiftService entry points remain authenticated and ordinary ADMIN_GIFT operations; compensation service uses the shared pure transaction helpers instead of calling GiftService APIs recursively or copying a second claim/delivery engine. Generic admin gift create cannot supply a source/reference; generic gift list/detail/update/preview/publish/cancel must not expose or operate a compensation campaign. Default nullable compensation metadata keeps old stored gift JSON compatible.

Create/update/preview/publish/cancel use request/version/reason guards. Compensation replay is keyed by current actor/requestId with a fingerprint including operation/incident/round and complete request. An identical replay returns the original committed response; mismatched reuse409, revoked roles cannot replay. The same requestId namespace covers incident and round operations. Round creation stores mapping and gift campaign atomically. Publish rechecks incident version, exact campaign version, normalized audience and preview token, then freezes recipients, immutable public content/rewards, incident history and audit/replay together. Token binds incident definition/version, round definition/version/number, selected sorted IDs, invalid IDs, receiving/supplemental reasons and previous claim summary. Previous claim changes may invalidate preview and require review again.

Preview shows at most10 safe recipient sample UUIDs, duplicate/invalid IDs, source and exact selection conditions, total recipients, total GOLD/XP, previous distinct claimed-user count, previous claimed-entitlement count and overlap with current selected recipients. The three previous-claim counts derive from one receipt query so distinct users are not confused with sums of round counts. Preserve claimed receipts after account deletion for reporting. Snapshot current ALL_REGISTERED IDs at publication; later registrations cannot receive that round.

Counts/aggregate GOLD/XP in new compensation responses are decimal strings for exact browser BigInt formatting; per-recipient GOLD/XP remain Int. Avoid reusing gift numeric-JSON aggregate responses as compensation transport. Reports reuse durable receipt/checkpoint accounting: eligible/pending/delivered/claimed/expired/cancelled/skipped and actual paid totals, explaining overlapping counters and never treating delivery as payout.

## Common delivery, wallet and player projection

The persisted gift campaign has optional server-owned compensation context. Wallet source derives exclusively from this stored property (`COMPENSATION` when present, legacy `ADMIN_GIFT` otherwise); generic request bodies cannot choose it. PostgreSQL and memory wallet histories share this rule. A next additive migration stores indexed campaign source and incident/round/replay tables, preserving V50 and all applied migrations. Round ID=gift campaign ID. Existing batch delivery/claim endpoints, locks campaign→recipient→user→stats, received-at boundary, maintenance gate, receipt replay, overflow rollback and cancellation remain authoritative. No independent delivery loop, player command, WebSocket discriminator or notification enum is added.

Compensation never reads event factors. V47's earned-asset allowlist excludes COMPENSATION; real PostgreSQL tests must prove wallet increases exactly once, leaderboard earned totals do not increase, and active×2 event definitions do not multiply it. Cancellation stops unclaimed delivery/claim, leaves claimed assets/receipts intact and reports skipped/deleted accounts. Restart uses existing durable PENDING/DELIVERED checkpoints.

`MailboxGift` gains only optional default-null `compensation` context containing incident UUID/key, round number, affected UTC bounds and receiving reasons VI/EN. No internal evidence, error code, operator ID or audit reason enters it. Existing old readers ignore the new field; missing metadata stays an ordinary gift. Server-generated bilingual body includes the player-safe incident description, exact affected UTC interval and receiving reason so existing clients still explain compensation. Expiry stays the existing mailbox field. New UI adds a small localized compensation/round label, renders stored text only, uses Mission GOLD/XP glyphs/tints, and retains authoritative profile refresh rather than adding amounts locally. No popup/push or new navigation destination is introduced.

## HTTP and UI

Requests use bounded strict JSON, exact Origin/CSRF and no-store; default page25/max100. Every route's typed contract is documented by its owning backend task before client work. Invalid JSON/body/input400, unauthorized401, forbidden403, missing404, conflict409, storage unavailable503 with no SQL/diagnostics. Mutation requestId `[A-Za-z0-9_-]{1,128}`, nonblank reason<=500 without control characters; optimistic versions positive and overflow safe.
