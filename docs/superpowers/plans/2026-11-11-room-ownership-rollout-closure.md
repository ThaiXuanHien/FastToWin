# Room Ownership Rollout Closure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close topology, account admission, presence, and cluster drain gaps so the production ownership candidate can earn a separate rollout acceptance receipt.

**Architecture:** A is the only public ingress and legacy authority; B is a private owned-room worker. A serializes each account's game lane, routes owned creates deterministically to A or B, and publishes presence from authoritative owned state. PostgreSQL fences new ownership admission by a durable policy generation; both runtimes continue existing work until global zero permits process drain and legacy rollback.

**Tech Stack:** Kotlin/JVM 17, Ktor/Netty, PostgreSQL/Flyway, existing signed peer transport and durable outbox, Redis presence/rate limits, Node/PowerShell local rehearsal runner.

**Spec:** `docs/superpowers/specs/2026-11-07-room-match-ownership-design.md`; production requirements/checkpoint in `docs/superpowers/plans/2026-11-11-room-ownership-production.md`; concrete closure analysis in `.artifacts/production-topology-review.md`.

## Global Constraints

- This document is a proposed implementation plan. No task below is implemented or accepted by this document. Current local Fault/Load receipts belong to the earlier candidate, not this future topology.
- The user has authorized ownership and presence production work. Continue implementation within that authorization; do not ask again merely because a previous plan guessed an approval boundary. This plan does not create a new paid cloud execution scope or perform any deployment.
- Preserve the existing dev fixture `pilot` path and its acceptance receipts. Production must not depend on a fixture marker or `FASTTOWIN_ROOM_OWNERSHIP_ACCEPTANCE=true`.
- Preserve current production authentication budgets, default rate policies and Redis namespace `prod_main`. Count public rate limits once at A; signed peer forwarding does not consume them again. Existing synthetic rehearsal source addresses remain local evidence only.
- The supported owned slice remains authenticated opted-in private `CASUAL` / `ORDER` 1v1. Unsupported modes, guests and non-opted-in accounts stay on A's legacy path.
- Keep PostgreSQL lease renewal 3 seconds, lease duration 12 seconds, recovery deadline 30 seconds and existing 25-second fault recovery target unless a separately tested change is needed. Use database time for durable admission/lease decisions.
- B receives no public domain or public application handlers. Keep `/internal` and `/internal/*` blocked by the existing web Caddyfile. No automatic public failover to B.
- A remains an ingress single point of failure. Exactly one legacy authority may run: stop/drain the previous A before replacement A restores legacy state; deployment must use one A replica with no overlapping legacy startup. This plan does not add a distributed fence to every legacy write.
- Peer DNS is currently resolved/pinned by `OwnerPeerTransport` construction. Process restart on the same address is insufficient redeploy evidence; a changed private address requires fresh exclusive-private DNS validation before readiness/rejoin.
- Do not edit V70–V72. Proposed V73/V74 names below assume V72 is still latest at implementation time; check migration head before allocating the next versions.

## Current names and proposed boundaries

`Main.main` currently constructs a `GameEngine`, calls `seasonLifecycleRepository.maintain()` and `engine.restoreActiveRooms()`, then installs `Application.gameModule`. That module starts all legacy/application jobs as well as `pilot.delivery.run()` and `pilot.runWorker()`. `OwnerPeerTransport`, `OwnerCommandRequest` and `OwnerOperation` all live in **`ownership/OwnerCommandRoutes.kt`**; there is no separate `OwnerPeerTransport.kt`. Existing operations are `COMMAND`, `RECONNECT`, `DISCONNECT`, requiring an existing room/epoch. `OwnedRoomEngine.create` currently chooses a random room ID and creates locally.

Existing presence seams are `Application.publishPresence`, `GameEngine.localPresence`, `GameEngine.enqueuePresenceUpdate`, `GameEngine.presenceDeliveries`, and private `GameEngine.rosterPresence`. Existing maintenance uses `MaintenanceRuntime.observe`, `MaintenanceService.refresh(activeMatches, allowEmptyDrain)` and `GameEngine.activeMaintenanceMatchCount()`. Existing `RoomOwnershipPilot.beginDrain()` is a process handoff; `canRollback()` reads global durable zero but does not coordinate all nodes.

Every new name/signature below is **proposed**, not an assertion that an API exists. Paths are repository-relative; Kotlin source/test files use package prefix `server/src/{main,test}/kotlin/com/hienthai/fastowin/server/`.

- [ ] Write signed private control tests with existing transport defenses and request idempotency. - [ ] Implement sequence: durable STOP_NEW; observe acknowledgements from A and B; close WAITING rooms through their current fenced owner without starting/debiting a match; allow active games, results departure/expiry and settlements to complete; read authoritative global zero; transition QUIESCING; call process `beginDrain`; collect fresh A/B process acknowledgements; read global zero again; transition DISABLED and emit proof.
