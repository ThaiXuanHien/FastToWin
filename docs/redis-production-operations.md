# Redis production operations

This is a proposed manual operating procedure, not a scheduled backup or authorization to deploy, access production, rotate credentials, or restore data. Redis is a single node with AOF persistence; it is not high availability or zero-loss recovery. Only entry rate-limit state is stored here. The proposed namespace is `prod_main`; changing it grants fresh quota and needs owner authorization.

## Backup and retention

Proposed maximum interval is 24 hours. An operator must decide when to run it and obtain the necessary authorization; no scheduler is configured. Retain encrypted local copies for 14 days using an approved encryption and key-management process. The archive created under `/tmp` in the Redis container is on the same service/volume environment and is not a durable independent backup. Copy the verified archive to an approved encrypted destination before considering the backup complete, and protect its access. Never put credentials in the archive or command arguments. There is no automatic backup or automatic restore.

The backup tool takes a unique 32-character lowercase hexadecimal tag and reads `FASTTOWIN_RATE_LIMIT_NAMESPACE` and `FASTTOWIN_REDIS_BACKUP_PASSWORD` from its environment. Run `/bin/sh /usr/local/bin/ftw-redis-backup.sh <tag>` in the authorized service environment. It fences and waits for local AOF fsync on one connection, pauses writes for at most 10 seconds, validates and copies the manifest and AOF files, checks hashes and fsyncs the archive. Its JSON result identifies the SHA-256 and size, not credentials. Check the result and independently verify the archive and its checksum before transfer. A failure, a missing acknowledgement, a changed file, an oversized archive, or a pause that expires invalidates the backup. Stop and investigate; do not treat a partial archive as valid.

The write pause can exceed the application's 200 ms command timeout and temporarily produce `RATE_LIMIT_UNAVAILABLE`/503 responses for new entry actions. Decide the timing and maintenance impact before production use; do not relax the timeout or silently fall back to memory. Pause expiry is a final bound if unpause fails. Confirm service recovery and investigate any failed unpause. Monitor and backup credentials must never be supplied to the game backend.

## Incidents and manual restore

A Redis failure rejects new protected actions; do not automatically change namespace, restore older quota or fall back to RAM. Stop if the backend startup gate fails, an archive or checksum is suspect, the data volume's identity is uncertain, credentials may be exposed, or ownership/authorization is unclear. Notify the owner through the established incident process and obtain an explicit decision. An owner may instead authorize a quota reset, understanding that it grants fresh quota and has a different user impact from restoring an older snapshot.

Restoring older quota can grant fresh quota or over-restrict users. Restore is manual, requires downtime, and cannot guarantee writes made after the backup. Before touching a service volume, obtain owner approval for the chosen snapshot and impact, stop the backend and Redis, and verify the target volume and a recoverable copy of its current contents. In an isolated staging directory, decrypt the chosen archive and verify its separately recorded SHA-256; inspect the archive without extracting it and reject absolute paths, traversal, duplicate names, links, nonregular files, extra files, more than 1,024 AOF data files, and compressed or uncompressed data over 256 MiB. Extract only the validated `appendonlydir/` files and `SHA256SUMS` into a new empty directory, verify every checksum and verify the manifest's file set against the extracted files. Do not extract an untrusted archive into the live volume.

With Redis still stopped, move the current `appendonlydir` aside on the verified volume, place the verified directory in its stead, and set ownership for the Redis user. Keep the prior directory for rollback until the owner approves its removal. Start Redis, verify authentication, AOF loading, service health and expected quota behavior, then restart the backend and verify its startup gate. Stop and preserve evidence if any verification fails. The bootstrap never restores an archive or resets quota automatically.

## Credential rotation

Generate each role secret independently from 48 cryptographically random bytes, encoded as 96 lowercase hexadecimal characters. Store and deliver them through the approved secret mechanism, never shell arguments, logs or game-backend configuration except the app credential. All current role secrets and any previous app secret must differ.

For an authorized planned app rotation, set the new `FASTTOWIN_REDIS_APP_PASSWORD` and the old value as `FASTTOWIN_REDIS_APP_PREVIOUS_PASSWORD`, then restart Redis to enable overlap. Verify both credentials, update the backend to the new app credential, and verify its startup and protected actions. Remove the previous value and restart Redis, then verify the old credential is denied and the new one works. Without the optional previous value only the current credential is accepted. Do not leave overlap indefinitely. Monitor and backup credential changes require a stopped maintenance operation: stop dependent operations, replace the relevant secret, restart Redis, update only its authorized client, and verify old access is revoked. There is no online rotation endpoint or admin Redis user.
