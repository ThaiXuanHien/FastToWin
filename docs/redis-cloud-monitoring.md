## Runtime boundaries and failure behavior

`prepare.mjs` accepts only the exact approved HTTPS `prometheus-….grafana.net/api/prom/push` destination, decimal tenant and a private collector host:port. Railway examples use `[::]:19121`, one replica and no public endpoint. Redirects, proxies from ambient environment, exemplars, native histograms and metadata shipping are disabled. Do not substitute a fallback endpoint or token after an error.

The collector launcher accepts only the96-lowercase-hex monitor password and writes an owner-only runtime file. It removes unrelated credentials before executing the nonroot collector. The sender launcher accepts only its stack-scoped metrics-write token and endpoint/tenant settings, prepares a private file and removes Redis credentials from its child environment. Keep the monitor and sender secrets in separate service-specific stores. Never pass either through CLI arguments, screenshots, logs, diffs or deployment reports.

Every current value and domain alert requires collector-up1, scrape-up1, and sample timestamp age in the inclusive0–60second interval using query time. Missing, old and future samples are unavailable. Last-success wall time is diagnostic only. WAL backfill must retain original sample timestamps: old samples must not become current health. Counter resets and historical gaps remain visible.

The sender WAL is unrelated to Redis AOF. The proposed production settings are cleanup5minutes, minimum retention5minutes and maximum2hours, one queue shard and a dedicated1-GB volume. Time retention is not a hard disk quota. A normal named Docker volume cannot portably enforce a1-GB hard capacity. The fixture includes a64-MiB owned tmpfs scenario under the unchanged256-MiB sender ceiling to model space errors and recovery; the executed scenario reached filler ENOSPC but did not establish an Alloy WAL failure and says nothing about physical disk durability. Do not claim restart backfill or oldest-sample expiry from process health, configuration validity or an HTTP204 carrying newer data. Use the actual timestamp receipts and mark any unsuccessful gate explicitly.

Controller clarification,2026-11-03: expiry applies to disk WAL including every checkpoint, not to the wire age of an already-buffered RAM queue. The fixture uses complete paused-copy snapshots, proves an old timestamp present before cleanup and absent afterwards, and requires recent timestamps still present. It records any older queued wire delivery separately; no `sample_age_limit` or queue policy is added. Missing disk proof cannot pass. The pinned implementation naturally rotates segments on cleanup; no manual volume/segment mutation is used.

`-Mode Storage` reuses owned setup/cleanup with an eight-minute post-start deadline and runs only the two remaining phases. It requires the same prepared matching decoder binaries as WALDiagnostic. The opt-in `-Mode FullOnly` runs only filesystem allocation/error/gap/recovery under a240second post-start deadline, using the already permitted accelerated WAL variant for natural forced flushes; this is fixture-only, not the production5minute setting. It captures mount/statfs/filler actual bytes and WAL size/allocated blocks before/after fill and after free. Full-filesystem acceptance records received timestamps throughout ENOSPC, distinguishes a gap from continued delivery and requires fresh recovery; it does not infer permanent loss or physical durability. A failed/inconclusive retention phase still permits the independent filesystem phase when safe. Cleanup includes containers, volumes, networks, built images, secrets and temporary WAL copies; any incomplete action/check fails the runner.

On shipping errors, collection must retain its fixed15second cadence. Never expand Redis ACLs, change rate-limit namespaces/quotas, restart the game, run persistence commands, or alter Redis to fix telemetry.
